# DECISIONS (living log; feeds NOTES.md)

| # | Decision | Why |
|---|---|---|
| D1 | Fridge identity = branch + fridge. A logger is a sensor with an assignment history (valid_from/valid_to). A fridge with no logger shows "no data" (grey), not green. | TL-0417 moved Walk-in -> Display 2; the history of both fridges must stay correct. |
| D2 | Threshold is per fridge (`max_temp`, default 5.0). Excursion = strictly above (> 5.0). | Different contents may need different limits; "above five" read literally. Question for Summer. |
| D3 | Units are a per-logger setting. The system only SUGGESTS Fahrenheit (median of the file > 20 means °F; 25-60 °F is a normal fridge range so confidence is high), a human confirms once, saved on the logger. | 38.3 °C is physically possible in a broken fridge, so deciding automatically is unsafe. Dividing by 10 (a wrong AI suggestion) gives a plausible-looking but wrong 3.83. |
| D4 | Always store the original value + unit next to the converted value. Changing a logger's unit later recomputes its readings. | Evidence for the inspector; a wrong unit choice can be corrected. |
| D5 | **Revised.** Gap = delta between readings > 2.5 x the logger's typical interval. Typical interval = the **most common** delta (ties -> the smaller), not the median. Never interpolate or fill. | Loggers record on a fixed interval, so the mode is that interval even when there are many gaps. With the median, Jerusalem in the email sample (deltas 15 and 135 min) gets a "typical" interval of 75 min and the 2h15m gap disappears. |
| D6 | Duration is a range: min = first high reading to last high reading; max = last OK reading before to first OK reading after. Primary value shown = max (conservative). | Example 06:00 ok, 06:15 6.0, 06:30 7.0, 06:45 ok -> min 15 min, max 45 min. |
| D7 | If a gap lies inside or next to an excursion, the duration is "unknown": only the lower bound is shown ("at least"). Same when the data starts above the threshold. | An honest report beats a confident wrong one. |
| D8 | **Revised.** Classification by provable time, not reading count: **spike** if max <= 30 min (provably short; labelled, not red); **sustained** if min > 30 min (provably long; red); **unverified** otherwise (could be short, could be long; orange); **ongoing** if the last reading is still above (red). | The first version ("up to 30 min = spike" plus a special rule for loggers slower than 30 min) was ambiguous: a single high reading on a 15-min logger has max exactly 30, and on a 30-min logger max 60. The new rule handles every interval with one sentence. Tel Aviv's 9.4 is a spike (max 30, boundary tested). |
| D9 | ERR / blank / text = measurement with status `error`. Not 0, not silently dropped. 3 or more errors in the window raise a grey data-quality warning. An ERR next to a high reading does not break the excursion (the logger was alive) but is noted. | |
| D10 | **Revised.** Warm-up trend: orange if the mean of the last 6 h is >= **1.0 °C** (first plan: 1.5) above the fridge's own median of the 7 days before that, AND the slope of the last 6 h is rising. Needs >= 3 days of history, otherwise no trend alert. Median, not mean. No ML. The fridge page shows when the warning first fired. | A fixed threshold alone would not have caught Rishon until too late. The Rishon test showed 1.5 °C fires only ~2.5 h (150 min) before a 3 °C fridge crosses 5 °C (warm-up 0.055 °C/h); 1.0 °C gives 10-20 h of warning for rises of 0.04-0.08 °C/h. The test pins >= 6 h of lead time. Cost: more false alarms from defrost cycles or a warm delivery (question for Summer). |
| D11 | Status: red = sustained or ongoing excursion in the window; orange = warming trend or unverified excursion; grey = no logger, no data, stale data, a gap or repeated ERR in the window; green = otherwise. All reasons are listed, not just the worst. Window: last 7 days (default, matches the weekly files) or last 24 h. | "No data" must never look like "fine". |
| D12 | Date format detected per file. ISO is unambiguous. For slashed dates, if any first part > 12 -> DD/MM; if any second part > 12 -> MM/DD; otherwise DD/MM (Israel) and the preview says it was a guess. | Israeli locale. |
| D13 | Timestamps kept as local wall-clock, no timezone conversion. | Files carry no timezone; all branches are in Israel. The DST change night is a known gap. |
| D14 | Duplicates: same logger + time + value -> dropped and counted. Same time, different number -> both kept, status `conflict`. Values compare as numbers (`3.90` = `3.9`). Status is computed from the whole set of rows, so import order does not matter and imports are idempotent. An ERR next to a number at the same time is not a conflict. | Summer pastes overlapping weekly files. |
| D15 | Stack: Node >= 22.13, `node:sqlite` (built in, no native build), Express, TypeScript via `tsx`, React + Vite, Tailwind CSS v4 via npm (`@tailwindcss/vite`), Recharts, `concurrently` for `npm run dev`. UI in English. CSV/TSV only. | The only constraint is "runs on a laptop from the README, no accounts, no paid services"; npm packages are free and install with `npm install`, so a normal, well-known stack is fine. `node:sqlite` avoids the one real install risk (native builds on Windows). A rebuild briefly switched to zero dependencies for an AI-environment reason; reverted, see AI_LOG. |
| D16 | Upload = "upload, then confirm". Two modes detected automatically: Summer's 5-column sheet and a raw logger file (time + temp). Also a paste box (copy from Excel). Preview is stateless: the client keeps the file text and sends it again on confirm; nothing is written on preview. | Matches how Summer works today; no temp files on the server. |
| D17 | Dependencies. Root dev: `concurrently`. Server: `express`; dev: `typescript`, `tsx`, `vitest`, `@types/node`, `@types/express`. Client: `react`, `react-dom`, `recharts`; dev: `vite`, `@vitejs/plugin-react`, `tailwindcss`, `@tailwindcss/vite`, `typescript`, `@types/react`, `@types/react-dom`. Nothing else (no multer: uploads are sent as JSON text, D16). | Smallest set that covers the fixed stack. |
| D18 | **Revised.** Versions are caret ranges of stable majors; the lock file is created by the first `npm install` and committed. | The earlier D18 contained claims from an AI tool (exact vitest version "4.1.12", "5.1.0 is under two weeks old", advisory names, "0 vulnerabilities") that were never checked. | D22 | "Now" for the dashboard = the latest reading in the database (`asOf`), shown on screen. | Files arrive weekly. Using the wall clock would turn every fridge grey a day after upload. |
| D23 | Stale = the fridge's last reading is older than max(2.5 x typical interval, 60 min) before `asOf` -> grey "no recent data". | Same rule as gaps, applied to the end of the data. |
| D24 | Two different values at the same time: excursion detection uses the higher one (conservative) and the report lists the conflict. | Food safety. |
| D25 | In the sheet the fridge is typed on each row, so each measurement stores its fridge. Logger assignment history is rebuilt from "change points" (logger X seen in fridge Y from time T); order-independent and idempotent.
